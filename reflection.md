# Reflection

**Applying the communication layer.** Each chart's title asks the question a manager would ask ("Which task types does the model handle well?"), and the "What this means" panel answers it in plain language, ending with a recommendation: fix reasoning and tool calling before switching models. All the numbers are averages, counts and shares ("share of answers scoring 70+"). There are no p-values, confidence intervals, standard deviations or test names. The box plot is the most technical element, so its title explains it ("box = middle half of scores") and doesn't name quartiles. Colour carries meaning, not decoration: green, amber and red for strong, acceptable and needs improvement on the category bars, and agree/disagree on the judge page.

**Dashboard vs. notebook.** I kept out how the data was made and checked: the Beta distributions, the cleaning rules, and the question of whether the small model gaps are real. Those live in `generate_evaluation_data.py`, `clean_evaluation_data.py` and `data_source.md`. A stakeholder needs to know that models barely differ here, not the test that proves it. The dashboard does include one methodological fact, on the judge page: how reliable the scores are. A 56% agreement rate changes how much weight the main dashboard deserves, so it is a "so what", not a "how".

**What I'd do differently.** I built the workbooks as code (`build_tableau_workbooks.py` writes the Tableau XML) so they can be reproduced and diffed. Hand-writing Tableau XML is fragile, though, and in a real engagement I'd build in the Tableau UI and keep the XML in version control. With real data, I'd replace the synthetic model column (randomly assigned, which is why models look identical) with actual model runs. I'd also make the "What this means" text depend on the filters, because static text can disagree with a filtered view. Finally, I'd check the dashboard with a non-technical reader before calling it done.
